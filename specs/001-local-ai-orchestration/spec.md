# Feature Specification: ローカルAIサブエージェント統括システム

**Feature Branch**: `001-local-ai-orchestration`

**Created**: 2026-09-29

**Status**: Draft

**Input**: User description: "Claude_LMStudio_サブエージェントシステム仕様案.txt の内容に基づく機能: Claudeを統括エージェントとし、AI Orchestrator経由でLM Studio上の複数ローカルAIモデルを専門サブエージェントとして使い分け、成果物をファイル管理し、Claudeが検証して修正ループを回し、タスク状態を管理し、ユーザーが最終確認・編集できるシステム。モデル定義は交換可能・後から変更可能。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - タスクを依頼して成果物を得る (Priority: P1)

ユーザーがClaudeに作業（例:「キャラクターAの設定を作成して」）を依頼すると、Claudeがタスクを分析して必要な能力を判定し、その能力に対応するローカルAIモデルが自動選択され、生成された成果物がファイルとして保存されてClaudeに返される。

**Why this priority**: 「依頼 → モデル選択 → 生成 → 成果物保存」が動かなければシステムの価値が成立しない。これ単体でMVPになる。

**Independent Test**: 1つのモデルを登録し、テキスト生成タスクを1件依頼して、成果物ファイルとタスク記録（使用モデル・プロンプト・日時）が保存され、Claudeが内容を取得できることを確認する。

**Acceptance Scenarios**:

1. **Given** 文章生成能力を持つモデルが登録済み、**When** ユーザーが設定作成を依頼、**Then** タスクが作成され、対応モデルが選択され、成果物が保存されてClaudeが取得できる。
2. **Given** 必要能力を満たすモデルが1つも登録されていない、**When** タスクを依頼、**Then** 「対応モデルなし」がClaudeに明示的に返り、タスクは失敗状態として記録される。
3. **Given** 対応モデルが現在ロードされていない、**When** タスクを実行、**Then** 必要なモデルが自動でロードされてから処理される。

---

### User Story 2 - 成果物の検証と修正ループ (Priority: P2)

Claudeが成果物を要求・必須項目・既存設定との整合性・形式などの観点で確認し、問題があれば問題点を整理した修正指示を出して修正版を得る。問題がなくなるまで繰り返し、完了できる。

**Why this priority**: 「Claudeが品質を確認する」ことがこのシステムの中核方針であり、ローカルモデルの品質ばらつきを吸収する要となる。

**Independent Test**: 意図的に必須項目が欠けた成果物を生成させ、検証で不合格となり、修正指示後の修正版（v002）が保存され、再検証で合格して完了状態になることを確認する。

**Acceptance Scenarios**:

1. **Given** 成果物が生成済み、**When** Claudeが検証して問題なしと判断、**Then** タスクが完了状態になる。
2. **Given** 誤字や形式など軽微な問題がある、**When** 修正指示を送信、**Then** 同じモデルが既存成果物をもとに修正版を作成し、新バージョンとして保存される（旧版は保持）。
3. **Given** 全体構成が要求を大きく外れている、**When** 再生成を依頼、**Then** 同じモデルが最初から作り直し、新バージョンとして保存される。
4. **Given** 現在のモデルでは品質が出ない、**When** 別モデルへの引き継ぎを指示、**Then** 別の対応モデルが処理を引き継ぎ、以降の版にそのモデル名が記録される。
5. **Given** 修正を繰り返しても合格しない、**When** 修正回数が上限に達する、**Then** タスクは失敗状態となり、ユーザーに判断が委ねられる。

---

### User Story 3 - モデルの登録・変更 (Priority: P3)

ユーザーが、モデルごとの能力・優先度・コンテキスト長・必要VRAMなどの定義を追加・変更・削除でき、システムを作り直さずにモデルを入れ替えられる。

**Why this priority**: 「特定モデルに依存しない」設計方針の実現手段。P1は最低1モデルの固定登録でも動くため優先度はP2より下。

**Independent Test**: 新しいモデル定義を追加し、その能力に合致するタスクで新モデルが選択されること、定義を無効化すると選択されなくなることを確認する。

**Acceptance Scenarios**:

1. **Given** 複数モデルが同じ能力を持つ、**When** タスクを依頼、**Then** 優先度が最も高く、かつコンテキスト長・VRAM条件を満たすモデルが選択される。
2. **Given** モデル定義を変更または削除、**When** 次のタスクを依頼、**Then** 変更が反映され、進行中タスクは影響を受けない。

---

### User Story 4 - 状態と履歴の把握、ユーザーによる最終確認・編集 (Priority: P3)

ユーザーがタスクの現在状態と履歴（使用モデル、修正回数、各版の検証結果）を確認でき、完了した成果物を自分で確認・編集・承認できる。

**Why this priority**: 完全自動化ではなくユーザーが最終責任を持つという方針に必要だが、コア処理の後で構わない。

**Independent Test**: 完了済みタスクを開き、状態・版履歴・検証結果が閲覧でき、成果物ファイルをユーザーが直接編集しても履歴が壊れないことを確認する。

**Acceptance Scenarios**:

1. **Given** 複数タスクが存在、**When** 一覧を確認、**Then** 各タスクの状態（未処理／処理中／確認中／修正必要／再生成中／完了／失敗）が分かる。
2. **Given** タスクが完了、**When** ユーザーが成果物を編集、**Then** 編集内容が最新版として保持され、AI生成版との区別が残る。

---

### Edge Cases

- モデルのロードに失敗した、またはVRAM不足の場合はどうなるか（別の対応モデルへのフォールバックまたは失敗状態＋理由の記録）。
- 生成が制限時間内に終わらない場合（タイムアウトとして扱い、再試行または失敗）。
- 入力がモデルのコンテキスト長を超える場合（適合するモデルの選択、または事前にエラー通知）。
- LM Studio自体が起動していない、または接続できない場合。
- 出力が指定形式（構造化データ等）として不正な場合（検証で不合格として扱う）。
- システム再起動などで処理が中断された場合、実行中だったタスクの状態をどう復元するか。
- 同一成果物に対して複数タスクが同時に書き込もうとした場合。
- 画像など非テキスト成果物を扱う場合の保存と検証方法。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、ユーザー依頼から作業単位のタスクを作成し、一意のIDを付与して記録できなければならない。
- **FR-002**: システムは、タスクに必要な能力（例: 文章生成、キャラクター設定、コード生成、画像生成）を指定でき、その能力に対応する登録済みモデルを検索できなければならない。
- **FR-003**: システムは、対応モデルが複数ある場合、優先度とコンテキスト長・必要VRAM等の制約に基づいて1つを選択し、選択結果を返さなければならない。
- **FR-004**: システムは、選択されたモデルが未ロードの場合に自動でロードし、必要に応じてモデルを切り替えて、常時全モデルを同時ロードしなくても動作しなければならない。
- **FR-005**: システムは、選択モデルへプロンプトを送信して生成結果を取得し、統括側（Claude）へ返さなければならない。
- **FR-006**: システムは、すべての生成結果をタスクごとにバージョン付きファイルとして保存し、旧版を上書きせず保持しなければならない。
- **FR-007**: システムは、タスクごとに、使用モデル、生成日時、プロンプト、生成結果、修正回数、修正履歴、検証結果、最終状態を記録しなければならない。
- **FR-008**: システムは、Claudeが成果物の検証結果（合格／不合格と問題点）を登録できるようにし、検証結果を該当バージョンに紐づけて保存しなければならない。
- **FR-009**: システムは、不合格の成果物に対し、次の3種類の修正方法を受け付けなければならない: (a) 同一モデルへの軽微な修正指示、(b) 同一モデルへの再生成、(c) 別モデルへの引き継ぎ。
- **FR-010**: システムは、修正回数の上限を設定でき、上限に達した場合はタスクを失敗状態にしてユーザーへ通知しなければならない。
- **FR-011**: システムは、タスクに次の状態を持たせ、状態遷移を履歴として記録しなければならない: 未処理、処理中、確認中、修正必要、再生成中、完了、失敗。
- **FR-012**: システムは、モデルロード失敗、接続不可、タイムアウト、不正な出力といった障害を検出し、原因を含むエラーとして統括側へ返し、状態を「失敗」または再試行可能な状態に更新しなければならない。
- **FR-013**: システムは、生成処理に制限時間を設け、超過時はタイムアウトとして処理しなければならない。
- **FR-014**: ユーザーは、モデル定義（名称、識別名、対応能力・得意分野、優先度、コンテキスト長、必要VRAM、推奨設定、出力形式、モデル種別、起動方法）を追加・変更・削除・無効化でき、変更が再ビルドなしで次回以降のタスクに反映されなければならない。
- **FR-015**: システムは、特定モデルの存在を前提とせず、モデル定義のみに基づいてモデルを選択しなければならない。
- **FR-016**: ユーザーは、タスク一覧・状態・履歴・各バージョンの成果物と検証結果を閲覧できなければならない。
- **FR-017**: ユーザーは、完了した成果物を確認・編集でき、編集内容は最新版として保持されつつAI生成版とは区別されなければならない。
- **FR-018**: システムは、Claudeが、タスク作成・モデル選択・エージェント実行・成果物取得・成果物検証・修正依頼・タスク完了の各操作を、ツールとして呼び出せる形で提供しなければならない。
- **FR-019**: システムは、中断後に再開した際、未完了タスクの状態と保存済み成果物を失わず、再開または失敗として明示できなければならない。
- **FR-020**: システムは、Claudeによる検証を経ない成果物を「完了」にしてはならない（サブAIの出力をそのまま採用しない）。

### Key Entities

- **タスク (Task)**: ユーザー依頼を表す作業単位。ID、依頼内容、必要能力、現在状態、状態遷移履歴、修正回数、成果物バージョン群への参照を持つ。
- **モデル定義 (Model Definition)**: 利用可能なローカルAIの登録情報。名称、識別名、対応能力、優先度、コンテキスト長、必要VRAM、推奨設定、出力形式、モデル種別、起動方法、有効／無効。
- **成果物バージョン (Artifact Version)**: タスクが生成した1つの結果。バージョン番号、生成元モデル、生成日時、使用プロンプト、内容、生成種別（初回／修正／再生成／引き継ぎ／ユーザー編集）。
- **検証結果 (Validation Result)**: 特定の成果物バージョンに対するClaudeの判定。合格／不合格、問題点一覧、確認観点、修正方法の指定。
- **修正指示 (Revision Request)**: 不合格の成果物に対する指示。修正方法（軽微／再生成／AI変更）、問題点、対象バージョン、引き継ぎ先モデル（AI変更時）。
- **能力 (Capability)**: モデルとタスクを結びつける分類ラベル（例: story、character_design、code、image）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ユーザーは1回の依頼だけで、人手によるモデル指定なしに、対応する成果物を受け取れる（モデル選択の手動操作が0回）。
- **SC-002**: 登録済みモデルの能力に合致する依頼の95%以上で、適切なモデルが自動選択される。
- **SC-003**: 検証で不合格となった成果物の80%以上が、修正ループ3回以内に合格する。
- **SC-004**: 全成果物バージョンについて、使用モデル・プロンプト・生成日時・検証結果が100%追跡できる。
- **SC-005**: モデル定義の追加・変更・無効化が、システムの作り直しなしで次のタスクから反映される。
- **SC-006**: 1つの成果物につき、ユーザーが5分以内に現在状態・修正履歴・最新版を把握できる。
- **SC-007**: モデルロード失敗・接続不可・タイムアウトの各障害で、100%のケースで原因付きの結果が返り、タスクが無反応のまま残らない。
- **SC-008**: 中断・再起動後に、保存済みの全成果物バージョンが失われない。

## Assumptions

- 利用者は個人または小規模チームで、LM Studioが同一マシン（またはローカルネットワーク内）で利用可能である。
- 統括役はClaudeで、システムはClaudeから呼び出せる形（MCPツール）で提供される。ツール名は元仕様案（create_task, select_model, run_agent, get_artifact, validate_artifact, request_revision, complete_task）に従う。
- v1では、同時に実行するモデルは1つ（逐次実行）とする。複数AIの並列実行、AI同士のレビュー、モデルごとの品質履歴学習は将来拡張として対象外。
- v1の主対象はテキスト系成果物（文章、設定、コード）。画像生成モデルは登録と選択の対象に含むが、画像品質の自動検証はClaudeの判断に委ねる。
- 成果物とタスク記録はローカルのファイル（tasks/ と artifacts/ 配下）として保存され、ユーザーが直接開いて編集できる。
- 修正回数の上限の既定値は3回とし、設定で変更できる。
- 検証観点（要求充足、必須項目、既存設定との整合性、形式、品質）の判定はClaudeが行い、システムは結果の保存と状態管理を担う。
- 認証・多ユーザー権限管理はv1の対象外（単一ユーザーのローカル利用）。
- コードのビルド・自動テスト、コスト／VRAM使用量の管理画面、モデル選択の学習は将来拡張。
